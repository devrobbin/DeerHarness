| 项 | 值 |
|---|---|
| **版本** | v1.1.0 |
| **更新时间** | 2026-09-11 |
| **关联 ADR** | ADR-0001、ADR-0012 |
| **变更摘要** | 专家评审修订：定位措辞与实现对齐（协同进化/质量目标分）；新增竞争格局、成功指标、价值主张证据栏；目标用户分主次；Non-Goals 改为决策规则 |

## 一句话定位

> **DeerHarness 是一个"以 Agent 团队为单位"的本地优先协同进化平台。**

它把 **PenguinHarness 的 Agent 生产与自进化能力**、**DeerFlow 2.X 的多智能体运行时**接起来，让用户**用一句话描述业务团队，系统自动组队、真实运行、评测、改进、再运行**——循环直到团队达到**设定的质量目标分**，全程有人工审批把关、有成本护栏、有版本可回滚。

> **措辞与实现的诚实边界（评审 ADR-0012）**：
> - **"协同进化"** 指评测以完整团队真实运行（主代理 + 子代理全链路）为单元、版本快照保证团队配置一致性；当前每轮改进为**单点方案**（主代理 soul / 某成员人设 / 工作流模板 三选一），多目标联合改进（bundle proposal）为远期方向。
> - **"质量目标分"** 当前是 LLM-judge 质量评分（0-100，基于任务完成度），不是业务结果指标（ACoS/GPM 等）；业务反馈信号接入为远期方向（见成功指标）。

## 解决的问题

| 痛点 | 现有方案的差距 | DeerHarness 的答案 |
|---|---|---|
| Agent 开发成本高、迭代慢 | 手写 prompt / 反复调参，缺少自动化评测-改进循环 | 一句话生成团队，评估→改进→审批→复测闭环自动迭代 |
| 长链路多智能体协作易失忆、上下文混乱 | 单 Agent 或简单编排难以稳定执行长任务 | DeerFlow 2.X 运行时：沙箱 / 记忆 / 子代理 / 持久化 |
| 单 Agent 优化易破坏团队协作协议 | 逐 Agent 单独优化，无团队级验证 | **以团队真实运行为评测单元**：每次改进都在完整团队上下文中验证，版本快照保证一致性 |
| AI 自我改进不可控 | 全自动进化无守门 | 人工审批门 + 负面样本记忆 + 验证轮 |
| 成本不可预期 | 无成本意识 | run 级用量统计 + 估算兜底，max_cost / token_capped 硬顶 |

## 竞争格局与为什么是我们

> 差异点均可在代码/文档中指认（括号内为证据位置）。

| 方案 | 它们做到什么 | DeerHarness 的差异 |
|---|---|---|
| **LangGraph / AutoGen / CrewAI** | 提供编排框架与多智能体抽象，但 Agent 定义、评测、进化全部自建 | 开箱即用的**团队模板资产**（8 个内置，可导入/导出/版本管理）+ 内建评测-审批-复测闭环（docs/05、fusion.py） |
| **Dify / Coze 等低代码平台** | 可视化编排单 Agent 应用，面向通用场景 | 面向**团队**而非单 Agent；本地优先自托管，数据不出本机；进化产物可回滚（docs/06、evolution_store.py） |
| **直接用 DeerFlow 2.X + 自研脚本** | 获得运行时能力，但"定义→同步→评测→改进"胶水层要自己写 | **融合桥**把 PenguinHarness 的 Agent 生产与 DeerFlow 运行时接通：同步/双轨注册/工具白名单映射/幂等评测全内置（docs/04） |
| **上游 PenguinHarness 单独使用** | 单 Agent 自进化（benchmark → 优化） | 补上**多智能体团队层**：团队编排、团队级评测、审批门、团队配置版本管理——两个上游都没有的层次 |

## 价值主张（Value Propositions）

> 每条附证据；标注"待验证"的表示需要真实运行数据补充（评审 P1-2 的诚实处理）。

1. **团队即产品单位**：8 个内置团队模板开箱即用（5 跨境 + 3 通用），可运行时改组、可导入导出、带版本管理。*证据：docs/06、fusion.py 模板资产化 5 端点。* ⚠️ 前置条件见 [02-产品设计 前置条件](02-product.md)。
2. **自进化但有人守门**：评估→改进→审批→应用→复测闭环。*证据：审批门默认开启（`require_human_approval=true`）、被拒方案进负面样本防重复、验证轮保证改进被评测（evolution.py）。量化效果（如"N 轮进化平均分 X→Y，成本 $Z，耗时 W"）**待验证**——需真实运行数据填入。*
3. **真实运行而非演示**：融合桥把 penguin 定义同步为 DeerFlow 2.X 运行时子代理，真沙箱、真工具、真成本。*证据：`run_and_wait` + Idempotency-Key 防重复执行、`subagent_stop_reason=token_capped` 显式暴露（deerflow_client.py）。*
4. **成本与安全是内建护栏**：RBAC（admin/developer/viewer）、max_rounds / max_cost / blocked_domains / token_capped 即停。*证据：护栏执行位置见 docs/05；已知缺口与绕过路径如实披露于 docs/07「已知缺口」。*
5. **可追溯可回滚**：每轮进化自动快照团队配置、版本得分曲线可对比、一键回滚（进化版本 + 模板版本）。*证据：`override_history` 历史表、rollback API（evolution_store.py、fusion.py）。*

## 目标用户

- **主用户：跨境电商运营团队**——初始 12 个月的唯一 GTM 场景（Amazon / TikTok Shop / 内容 / 履约财税的"运营团队数字分身"）。
- **次用户：Agent 平台开发者**——把本项目作为"Agent 生产 × 运行时缝合 + 进化闭环"的开源参考实现（不做商业化承诺）。
- 通用团队模板（research/support/dev-ops）的定位是**验证团队模型不绑定跨境领域**（引擎通用性证明与生态示例），不作为独立 GTM 方向（见 docs/06）。

## 非目标（Non-Goals，含重估触发条件）

> Non-Goals 是"初始不做 + 重估条件"的决策规则，不是永久禁止（评审 P1-5 修订）。

| 非目标 | 重估触发条件 |
|---|---|
| 不替代 PenguinHarness 的 Agent 生产 / 不替代 DeerFlow 的运行时——只做编排与进化层 | 上游能力缺失导致编排层无法闭环时，评估最小补充 |
| 公有云 SaaS：初始不做（本地优先 / 自托管） | 模板共享需求被 ≥3 个外部部署实例验证后重估（对应远期"模板共享仓库"） |
| 通用低代码平台：不做流式编排画布等通用能力 | 主用户场景饱和、通用模板需求显著增长后重估 |

## 成功指标（North Star）

> 产品当前处于"功能闭环"阶段，价值闭环需要验证轨道（评审 P1-6/P1-7 修订）。

- **北极星**：每月被真实运行 ≥N 次的活跃团队数（N 待首个试点数据校准）。
- **支撑指标**：进化任务达标率；平均得分提升幅度/轮次；定时巡检周活跃数；模板导入/导出次数。
- **护栏指标**：单团队月成本上限内运行率；进化方案审批拒绝率（过高说明改进质量差）。
- **验证轨道（v0.8 目标）**：3 个真实跨境卖家试点，跑通"组建团队→真实运行→发起进化→审批→回滚"各 ≥5 次，产出首个进化前后对比案例。

## 与上游的关系（DeerFlow 2.X 为既定基准）

| 上游 | 定位 | 本项目消费的能力 |
|---|---|---|
| **PenguinHarness** | Agent 工厂 + 训练场 | Agent 定义（system prompt / tools）、benchmark、官方 Docker 镜像、Machines（远程部署通道，只读展示） |
| **DeerFlow 2.X** | Super Agent Harness（运行时） | threads / runs（含 wait + Idempotency-Key）、subagents、sandbox、PAT 认证、token_budget、scheduled-tasks |

> **约定：DeerFlow 以 2.X 为基准。** 融合桥按 2.X 契约（PAT + 幂等 + 编程式子代理 API）实现；对旧版 OAuth2 表单登录仅保留兼容回退，不作为设计基准。
