# 提案: 进化实验室 — 团队级 / 工作流级进化(审批队列)

## 现状(调研结论)
- 评估机制完整可用:fusion/evaluate + dh-benchmark 5 用例 + LLM 评分 + eval:* traces 趋势
- 进化生命周期是空壳:evolution 的 start/status/versions 全是 501;三个组件(任务面板/实时追踪/得分图)造好未接线;WS 频道无人 publish
- Safety 四项配置(轮次/成本/审批/领域)无任何代码执行
- 团队/工作流配置硬编码在 TEAM_TEMPLATES,不可写 → 进化必须先有可写存储

## 一、三层进化目标
| 层级 | 目标 | 评估方式 | 可改进对象 |
|---|---|---|---|
| Agent 级 | 单 agent(已有,保留) | dh-benchmark | (保持 evaluate) |
| **工作流级** | {团队, 工作流} | 该工作流 task 作为评测语句 + 通用用例 | **workflow.task 文本** |
| **团队级** | {团队} | 团队专属用例 + 通用用例 | **主代理 soul + 成员 systemPrompt** |

## 二、可进化配置存储(gateway/evolution_store.py,SQLite)
- `config_overrides`:team_id + workflow_id(NULL=团队级)+ field(workflow_task/soul/member_prompt)+ 目标成员 + value + version + applied_at
- 融合:TEAM_TEMPLATES 基础 + overrides 覆盖 —— team/templates、team/run 的 `_sync_orchestrator`/`_resolve_workflow_task` 全部读合并后配置 → **进化产物立即被团队编排使用**
- 每版本保存配置快照,可追溯可回滚

## 三、进化闭环(重写 /api/evolution,替换 501 桩)
每轮循环: **评估 → LLM 改进建议 → 审批门 → 应用 → 复测**
1. `POST /api/evolution/start` {target_type, team_id?, workflow_id?, agent_id?, max_rounds, target_score} → 建任务后台执行
2. 评估:复用 fusion 的 `_run_case`+`_score_replies`(deepseek 评分)
3. 改进:LLM 生成结构化方案 {目标对象, 新文本, 理由}(受 blocked_domains 过滤)
4. **审批门**:require_human_approval=true → 方案入审批队列,任务挂起;`POST /tasks/{id}/approve|reject` 后继续;false → 自动应用
5. 应用:写 config_overrides(新版本) → 复测同用例 → 得分对比
6. WS publish 到现有 `evolution/{task_id}` 频道(实时追踪组件立刻可用)
7. 端点:`GET /tasks`(含目标信息)、`GET /tasks/{id}/status`、`GET /tasks/{id}/versions`{version,score,change_summary}、`GET /tasks/{id}/approvals`、approve/reject
8. **护栏落地**:max_evolution_rounds 限轮数;max_cost_per_evolution 累计评估成本超限停止;blocked_domains 过滤改进建议
